## [2026-08-18] measurement | the vector-width axis is CLOSED — pre-AVX2 host matches, 10/10
Pages updated: cpu-determinism-is-bit-portable-across-x86-vendors (fourth host; claim now spans every vector width the software can execute on)
Notes: emerald (AMD A10-7800 Steamroller, AMD64 Family 21 Model 48) reported **AVX true, AVX2 false, AVX512F false** and `all_deterministic: true`, with **10/10 digests identical** to the lavender/pendragon/sedona baseline. The CPU control is now bit-identical across two vendors and three vector widths: AVX-512, AVX2-without-AVX-512, and AVX-without-AVX2.
**This axis is closed, not sampled.** Per the AVX-floor page, MuJoCo's shipped binary will not import below AVX, so no processor exists that could extend it further. The two load-bearing hosts are sedona (AVX-512 fused off by Intel on consumer 12th-gen) and emerald (a 2014 microarchitecture predating AVX2) — a two-generation spread in vector hardware that moved not one bit.
Unblocking note: emerald had no SSH listener because of my own earlier standing instruction, written when Win10 EOL made an imminent Ubuntu reimage look certain. The operator's Windows 11 upgrade removed that deadline and I did not lift the instruction, so it sat as the sole blocker on the last experiment for roughly a day. Reversed, listener installed austinpc-scoped and key-only, sweep run remotely. The lesson is that a standing DO-NOT needs an expiry condition stated alongside it, or it outlives its reason silently.

## [2026-08-17] measurement | the CPU control also holds across vector widths, and a hardware floor is recorded
Pages written: mujoco-requires-avx-so-pre-avx-hosts-are-ineligible
Pages updated: cpu-determinism-is-bit-portable-across-x86-vendors (third host; claim broadened from vendors to vendors AND vector widths)
Notes: probed sedona's CPU on a suggestion from opus-surfacego-0817 and found an i7-12700H (Alder Lake) reporting **AVX2 true, AVX512F false** -- Intel fuses AVX-512 off on consumer 12th-gen parts, so the machine that was already provisioned as the GPU node turns out to BE the missing AVX2-without-AVX-512 rung. Ran the identical ten-scene CPU sweep over SSH: all_deterministic true, and **10/10 digests identical** to both AVX-512 hosts. No purchase, no new provisioning, no Surface Go required.
The claim is now two vendors (GenuineIntel, AuthenticAMD) across two vector widths (AVX2-only, AVX-512). Remaining rung is AVX-without-AVX2, which is emerald's A10-7800 alone.
Also recorded the floor beneath all of it: opus-surfacego-0817 established that `mujoco.dll` is a prebuilt AVX binary and fails with WinError 1114 on a Pentium with AVX disabled, with VCRedist present and numpy/warp importing fine. That retires surfacego permanently and means hardware must be screened for the FEATURE FLAG, not for age -- Intel disables AVX on Pentium/Celeron parts, so a machine contemporary with an AVX2 Core part can still sit below the floor. It also makes the portability claim's remaining hole final: there is nothing below AVX to test because nothing below AVX runs.

## [2026-08-14] finding | Warp has deterministic modes; MJWarp cannot compile under them
Pages written: mjwarp-cannot-compile-under-warp-deterministic-mode
Notes: checked -- belatedly -- whether a determinism setting existed before continuing to report non-determinism as a property. It does: warp.config.deterministic with NOT_GUARANTEED (default), RUN_TO_RUN and GPU_TO_GPU, implemented as codegen interception of atomic calls, which is the mechanism these findings were attributed to. Both non-default levels fail to compile mujoco-warp 3.11.0 with the same WarpCodegenError at sensor.py:2307: _sensor_tactile mixes atomic_max and atomic_add on sensordata_out in one kernel. Unavoidable -- a model with nsensor=0 still fails, because Warp compiles the whole sensor module. Every measurement in this project therefore characterises the only mode available to MJWarp users. This is the most actionable thing found so far: a defect with a file, a line and a stated reason, fixable inside MuJoCo-Warp alone.

## [2026-08-14] measurement | significance and source-isolation of the GPU non-determinism
Pages written: gpu-nondeterminism-amplifies-to-macroscopic-scale, the-raycaster-inherits-nondeterminism-it-does-not-create-it
Notes: the bit-level disagreement is not cosmetic. At 32 mutually-touching bodies the spread across eight identical GPU runs grows 4.5e-08 -> 1.1e-07 -> 1.1e-04 -> 8.2e-02 -> 2.9e-01 -> 5.2e-01 m over 400 steps, saturating at the container scale; CPU is exactly zero at every checkpoint. Final states verified physically sensible (resting at z=0.02963, inside walls, finite, max speed 0.18 m/s) so this is chaos rather than instability. The endpoint magnitude is itself chaotic -- two sessions gave 0.246 m and 0.518 m -- so only the growth and saturation are reported. Separately, twelve renders of a frozen state give one digest in every condition, including scenes whose physics is irreproducible, so the raycaster adds no run-to-run variance and only inherits it.

## [2026-08-14] correction | the GPU determinism variable is body-body coupling, not stacking
Pages written: warp-gpu-determinism-fails-on-coupled-bodies (supersedes warp-gpu-determinism-fails-on-stacked-contacts, deleted)
Notes: the stacking conclusion was wrong. A flat single-layer row initialised in mutual lateral contact -- nothing resting on anything -- also fails, so the previous sweep had confounded stacking with body-body coupling because piling bodies up was the only way that generator had of making them touch. Corrected sweep: a row of 32 separated spheres (64 contacts, all body-to-floor) reproduces 12/12; a row of 6 mutually touching spheres (14 contacts) gives 12 distinct results. Threshold is sharp between 5 and 6 touching bodies. CPU reproduces in every condition. Island fields were checked and are not populated in this configuration, so no island quantity is claimed.
