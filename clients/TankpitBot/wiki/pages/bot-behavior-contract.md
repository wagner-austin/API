# Bot Behavior Contract

The single source of truth for *what the bot must do* and *how each behavior is verified*. When proposing a fix, consult this page first to know what else might break.[^1]

This contract complements [[client-state-machine]] (the JS client's state machine) and [[tank-freshness-model]] (our wire-presence semantic). The state machine describes the *server protocol*; this page describes *our bot's obligations*.

Format: each row in each section has **MUST / MUST NOT / Verified by**. "Verified by" names the smoke assertion and integration test that locks the behavior in. If a behavior is not yet verified, that's flagged explicitly — every claim here must eventually point to a test. The test idioms those rows name (and the DI rules they follow) are in [[testing-patterns]].

### 1.4 Control verbs (steering a running fleet bot)

The operator's need, carried from 95e5da95 into board task 97975b5d: peel one bot off a long human fight without taking it out of the world. `STOP` ends the session, so a running bot takes verbs short of it.[^4]

| Verb | What it writes | Effect |
|---|---|---|
| `hold HUNT` / `hold COLLECT` | `manual_mode` | Pins the durable owner. This is the same pin the single-session service's mode picker writes, so it skips auto-arbitration, including the hunt-only-when-full gate (§3.1). That was already true of the pin; the verb adds no new hunt path. |
| `disengage` | `clear_combat_target` + the dropped target into `blocked_combat_targets` + `manual_mode = COLLECT` | Drops the combat lock and forages until `release`. The bot stays in the world. The block is the one the engage path already writes to walk away from a target, and it lasts one kill cooldown (30 s default). Without it, the lock-free COLLECT tick re-fought the enemy just left through collect return fire: on sedona, six opportunity shots at purple-1 in the twelve seconds after the verb. That is the `-1` variant `collect_return_fire`'s docstring records. |
| `wind_down` | `wind_down = True` + `manual_mode = None` | The same flag the session clock and the kill target raise (§1.2): no new engagements, top off, exit `session_complete`. It clears the pin because a pinned owner skips the arbitration that holds the stocked exit. A live locked fight still finishes first, as it does for the clock, so `disengage` then `wind_down` leaves one immediately. |
| `release` | `manual_mode = None` | Auto-arbitration again. |
| `doctrine <skirmish\|swarm\|duelist\|passive>` | `config.doctrine` | Rewrites the doctrine in place, because a bot reads its environment config once at `Bot.__init__`. The fleet row and the spawn record take the new doctrine too, so an adopting manager and a restart see what now runs. |

| Aspect | Contract |
|---|---|
| MUST | Ride ONE channel: a `CONTROL` file beside `STOP` in `runs/bot/<instance>/`, written atomically by the fleet manager, taken at the top of every tick and removed on ingest. The in-process mode bridge steers only the single-session service; it is not a second fleet channel. |
| MUST | Validate every command with the one decoder, at the manager (`POST /bots/{instance}/control?verb=&argument=` answers 400) and again at the bot. An unknown verb, a missing argument, or an argument on a verb that takes none is a hard error at both ends. A file that is not JSON raises, and it is consumed first so the error does not repeat every tick. |
| MUST | Refuse a second verb while the first is still pending (HTTP 409), so no verb is overwritten between two ticks. Refuse an unknown instance (404) and one that is not running (409). |
| MUST | Read the directory the manager writes: the service child's stop path is `bot_stop_file(instance)`, and CONTROL sits beside it. The first live run found the child watching `runs/state/<instance>/` instead, so neither a verb nor the fleet's own stop reached it ([[fleet-lifecycle]], the drain section). Spawn clears a STOP or CONTROL that a predecessor left untaken in a reused slot. |
| MUST NOT | Add a hunt gate or bypass one. Every verb writes a field an existing path already reads. |
| MUST | Wind a GATHERER down like every other role, from the verb or from the session clock (board task e956e3c8). "Stocked" is per role (`wound_down_stocked`): a gatherer never fights, so its bar is a full tank of fuel alone (`hunt_fuel_floor`), and every other role's bar stays `should_exit_collect`. `_select_owner_mode` reads the wind-down branch before the gatherer's fixed COLLECT, and a winding-down gatherer whose cascade is exhausted exits `session_complete` instead of holding. Before this, the gatherer return came first and the fighter's bar was the only one, which a gatherer's always-closed hunt gate never met, so a bounded gatherer session ended only on the hard tick budget, mid-action. |
| Verified by | `tests/bot/test_control.py` (codec round trip, every refusal, the file taken once, each verb's state; the pinned-stocked wind-down through the real `decide()`, where the flag alone still hunts and the verb exits `session_complete`; and disengage through the real `collect_return_fire` on a confirmed attacker, where the lock cleared alone still fires and the verb's block silences it); `tests/service/test_fleet_control_verbs.py` (the manager's write, pending, unknown and finished refusals, doctrine on the row and the record, and the route's 200/400/404/409); `tests/bot/test_tick_loop_lifecycle.py::TestControlFile` (a real file written by the manager's writer changes the AI state at the next tick and is consumed); `tests/service/test_constants.py` (the service's stop path IS `bot_stop_file`); `tests/service/test_fleet_slot.py` (a reused slot's untaken sentinels are cleared at spawn); `tests/bot/ai/test_strategy_coverage.py::TestGathererRouting` (a winding-down gatherer on a full tank with empty weapons exits `session_complete`, one unit short it collects, and on the exhausted cascade that holds a working gatherer it exits instead). Live on sedona, 2026-09-29, Artax in Practice: `hold HUNT` flipped the owner from COLLECT to HUNT with a new lock. `doctrine passive` reached the row, the spawn record and the bot's log. `release` returned the owner to auto-arbitration, which kept HUNT for the held lock. `wind_down` finished the live fight (a kill), then exited `session_complete` fully stocked at fuel 1100. `disengage` (release v0.1.0-f101d8bc7) dropped lock 565 on orange-3 mid-fight: the next tick was an equipment pickup under COLLECT, then fuel and a frontier hop, with no shot at anyone. A fleet `stop` was detected by the child within a second.[^5] A gatherer (release v0.1.0-1b5a5281c) collecting fuel in Practice took `wind_down` and exited `session_complete` four seconds later, fully stocked at fuel 1100, return code 0.[^6] |

## 2. Perception (world state)

### 2.1 Tank tracking

| Aspect | Contract |
|---|---|
| MUST | Every tank in `world_state["tanks"]` carries the three freshness timestamps (`timestamp_ms`, `last_wire_seen_ms`, `last_position_update_ms`) plus a `liveness` field. See [[tank-freshness-model]]. |
| MUST | `timestamp_ms` advances on every observation (wire or map). |
| MUST | `last_wire_seen_ms` advances ONLY on `is_wire_sourced=True` observations. |
| MUST | `last_position_update_ms` advances ONLY on observations whose position is authoritative (`position_is_authoritative=True`) and that carry a `position`. Wire position messages are authoritative, and so is the 0x4C MapData snapshot (`is_wire_sourced=False`), so a stationary target stays position-fresh after a map open without the snapshot claiming wire presence. Radar EnemyDetect and DOM-scraped registry refinements are not authoritative. (Corrected 2026-09-29: this row said wire-sourced only, which predates MapData's authoritative flag.) |
| MUST | `liveness` is one of `alive` / `deactivated`. 0x41 Deactivation → `deactivated`; corpse-direction wire (`direction >= 32`) → `deactivated`; wire-sourced position update with alive direction → `alive`. |
| MUST | 0x58 TankRemove is a NO-OP at the registry level. 0x58 is *tracking removal*, not a kill — verified 2026-06-20 (orange-5 got 5 TankRemove events across 2 actual kills). The earlier behaviour deleted the entry from `tanks`; that caused the bot to abandon pursuit of locked targets that merely teleported out of viewport (live capture 2026-06-22 — bot fired 1 homing then dropped the lock). Keeping the entry lets `find_locked_target_pursuit` keep firing toward the cached coords until 0x41 Deactivation arrives or `timestamp_ms` goes stale. |
| MUST NOT | Treat 0x58 as a death signal. Use `0x41 Deactivation` (it flips `liveness="deactivated"` and routes through the kill cooldown). |
| MUST | **0x29 TankExit deletes the registry entry (2026-08-14, flag s11-6).** 0x29 is the room-wide "left the game / eliminated" announcement (the client banner's source) -- NOT 0x58 tracking churn, which stays a no-op. Run arterial 2026-08-13: the 0x29 for Artax arrived at 23:39:17 as a diagnostic-only event, and the registry ghost powered a ~75 s map-open/teleport/shoot chase (23:41:43-23:43:03) until a shot's err=3 friendly-fire receipt disproved what the wire had already announced. Deletion releases any held lock through the existing gone-from-registry pursuit path (`find_locked_target_pursuit` -> None) and drops the tank from every threat list; a rejoin re-adds it on first observation. Verified by `tests/sniffer/test_world_state_dispatch_tank.py::TestDispatchTankMessages::test_dispatch_tank_exit_deletes_the_registry_entry`. |
| Verified by | `tests/world_state/test_mutations_tanks.py::TestRemoveTank::test_keeps_tank_in_registry` (0x58 is no-op); `tests/world_state/test_mutations_tanks.py::TestDeactivateTank` (0x41 sets liveness); `tests/world_state/test_tank_observation_invariants.py` (the three freshness stamps, one class per invariant); `tests/bot/ai/test_hunt_pursuit.py::test_hunt_engage_fires_homing_when_locked_target_left_viewport` (pursuit fires while target is out of viewport).[^9] |

## 3. Decision-making

### 3.1 Mode selection

| Aspect | Contract |
|---|---|
| MUST | Mode selection is deterministic given (world_state, self_state, config). No randomness. |
| MUST | **Hunt only when full (user contract 2026-07-25):** HUNT entry requires `fuel >= fuel_capacity(rank)` AND duals+homings at `inventory_capacity(rank)` AND extra radars >= cap-5, every bar rank-derived ("it should never hunt if it is not full on everything except -5 max radar"; "just determine max fuel based on the tank rank"). Nothing overrides this: the 2026-07-13 cardinal-adjacent override was deleted 2026-07-25 after it produced the practice-room fight-to-death (see §5). A held HUNT releases only on a COLLECT trigger, so spending ammo mid-fight does not thrash ownership. |
| MUST | COLLECT entry uses `should_enter_collect`, which fires when ANY of: (1) `fuel <= fuel_low_threshold` (interrupts even an active combat target); (2) **Weapon emergency** -- any reserve below its *break* threshold (dual / homing < 4 or radar < 5) -- interrupts even with an active combat target; (3) **Between kills** -- `combat_target_id == -1` AND anything short of the full-tank bar above. The unified COLLECT mode replaced the historical `RECOVER_FUEL` + `RECOVER_EQUIPMENT` split 2026-06-24; the fixed resume thresholds (25/25/20) were replaced by the rank caps 2026-07-25. |
| MUST | **Partial mid-fight restock vs humans (user ruling 2026-07-31: "its not necessary to full restock but to do partial restocks so the bot can keep fighting the human... right now it felt like the bot will leave and peace out frequently so its not fun to engage"):** while a combat lock on a HUMAN-classified target is held, COLLECT's exit bar and HUNT's entry bar both drop from the full-stock bar to the combat-resume bar (`human_fight_resume_permitted`): fuel ≥ the resume floor (same 750-at-defaults formula as the break latch), duals AND homings ≥ `inventory_capacity(rank) // 2` (12 at private — break at <4, resume at half-cap keeps the hysteresis band wide), extra radars ≥ `min(combat_radar_min(rank), 2 × radar_break_threshold)` (10 at private — the bare break bar of 5 would be a zero-width band). The fuel bar and the gatherer role bar are untouched. ### 3.2 HUNT acquisition

| Aspect | Contract |
|---|---|
| MUST | Use `analyze_threats` to score candidate enemies. Sort by human tier, then distance, then finish-priority, then freshness. |
| MUST | **Human-priority targeting (user doctrine 2026-07-28: "farm bots but prioritize any human player that logs in"; hardened 2026-07-29: "unlimited distance for humans... this is the real deal"):** human-classified enemies outrank every practice bot regardless of distance, at all three selection points — visible threats, map-level acquisition, and the dot-relay travel target. **Unlimited-distance pursuit (2026-07-29):** an unaffordable rank-window human on the fresh map PREEMPTS every affordable practice bot at target selection — the acquisition step relays toward the human (`human_pursuit_travel_target` + `relay_toward`, `bot/ai/hunt_relay.py`) instead of farming, and a LOCKED human who teleports beyond the fundable range is chased leg-by-leg with the lock held (each relay leg closes distance AND refuels on the landing pickup). Locks are still never switched mid-fight (same-day follow-up: "finish the kill then the human player will be the next target"). When no relay leg helps (no progress dot, tank at capacity), the bot farms the affordable bot and re-evaluates on the next map — the pursuit never deadlocks the session. ### 3.3 Combat shoot gates (`engage_target`)

Every shoot path (direct engage, close-in shot, refresh-then-engage, locked-target pursuit) reaches one chokepoint, `engage_target`; the private `_combat_shoot` this heading once named was collapsed into it.[^11]

| Aspect | Contract |
|---|---|
| MUST | **Hit/miss = per-shot ammo consumption (2026-07-02).** The ShootEvent `weapon` field is the server's per-shot ammo ledger: `weapon > 0` = one dual/missile/homing debited = HIT (even with `victim_id=-1` on off-viewport pursuit impacts); `weapon = 0` = free single at empty ground = MISS. `victim_id` is kill-attribution metadata only, never the hit discriminator. (Wire proof: run 2026-07-02 01:21, five `weapon=3` `victim_id=-1` pursuit homings killed orange-3 while the old classifier logged five misses.) |
| MUST | **Viewport-clamped aim (2026-07-03):** every `shoot` dispatch aims inside the visible 16x16 viewport — the server rejects any aim outside it with 0x52 code 0 ("You can't do this"; live run 2026-07-03 20:34 drew five rejections aiming at a pursuit target 5 rows below the viewport). The aim is only a hint: the wire-proven snipe fires at an in-viewport ground tile with the target's `tank_id` and the server picks homing, whose seeker tracks the real target (`weapon=3` hit from the target's vacated tile, same run). ## 7. How to use this page

**Before proposing a bot-behavior fix:** read the relevant section. If the change affects a MUST/MUST NOT, list which one and what test will be updated. If the change affects an anti-pattern's prevention mechanism, confirm the test still passes.[^1]

**When `make smoke` fails:** the failing assertion maps to a section here (`smoke[N]` references). Open that section to know what the bot was supposed to be doing and which other behaviors might be entangled.[^3]

**When `make check` integration tests fail:** the test name maps to a row here. The contract row tells you the broader behavior that test guards.[^3]

**When you add a new behavior:** add a row here first (MUST / MUST NOT / Verified by), then write the test, then implement. Contract-first prevents drift ([[coding-standards]]).
